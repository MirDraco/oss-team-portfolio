# 結網(결망) - 모두와 연결하다
## 순천향대학교 컴퓨터소프트웨어공학과 오픈소스SW활용 H조 팀프로젝트
> 여섯 명의 배움과 코드를 엮어, 하나의 웹사이트를 만듭니다.

팀원들의 소개와 프로젝트, 협업 과정을 한국적 디자인으로 담아내는 팀 포트폴리오 웹사이트를 제작합니다.

**현재 단계:** 기획·설계 및 초기 파일 준비. 기능 구현·통합·배포는 진행 예정입니다.

**주요 링크:** [GitHub 저장소](https://github.com/MirDraco/oss-team-portfolio) · [작업 현황](https://github.com/MirDraco/oss-team-portfolio/issues)

**GitHub Pages:** [GitHub Pages 링크](https://mirdraco.github.io/oss-team-portfolio/)

## 💡 웹사이트 콘셉트

### 프로젝트 콘셉트
한옥과 전통 문양에서 영감을 받은 색상과 디자인으로 한국적인 분위기를 표현할 예정입니다.

### 팀명과 표현 방향
결망(結網)이라는 이름을 바탕으로, 각자의 배움과 코드를 엮어 하나의 결과물을 만든다는 메시지를 표현하고자 합니다.
한옥의 구조와 전통 문양에서 영감을 받아, 팀원·프로젝트·활동 기록을 연결하는 **현대적인 한국적 UI**를 지향합니다.
- 표현 방향: 차분한 색감, 정돈된 여백, 절제된 전통 문양
- 우선순위: 장식보다 내용의 가독성과 페이지 이동의 편리함

## 📍 협업 방식
기존 README의 규칙을 바탕으로 정리한 작업 방식입니다. 아래 세부 절차는 팀 검토 후 확정합니다.
### 전체 작업 흐름

처음 한 번은 `main`에서 `dev`를 만들고, 각 작업은 최신 `dev`에서 개인 기능 브랜치를 생성해 시작합니다.

```text
Issue 작성 → 최신 dev에서 개인 기능 브랜치 생성
→ 직접 구현·실행 확인 → 커밋·push
→ dev 대상 PR → 동료 리뷰·수정 → dev 병합
→ 통합 테스트 → dev에서 main으로 PR·확인·병합
→ GitHub Pages 배포 확인 → 기록 갱신
```

### 브랜치와 커밋
| 브랜치 | 용도 |
| --- | --- |
| `main` | 통합 확인을 마친 공개용 코드, GitHub Pages 배포 기준 |
| `dev` | 개인 기능을 합치고 페이지 간 연결과 전체 동작을 확인하는 통합 코드 |
| `feature/개인-기능` | 최신 `dev`에서 생성하는 개인별 작업 브랜치 |
- 기능 작업은 `feature/개인-기능` 브랜치에서 진행합니다.
- 예: `feature/minchan-members`, `feature/yunha-main`, `feature/donggeun-common-ui`
- 개인 브랜치의 변경은 PR과 다른 팀원의 리뷰를 거쳐 `dev`에 병합합니다.
- `dev`에서 통합 테스트를 마친 내용은 `dev → main` PR로 최종 확인 후 병합합니다.
- 기능 변경은 `dev`와 `main`에 직접 push하지 않고 PR을 거쳐 반영합니다.
- 새 작업은 그때의 최신 `dev`에서 새 브랜치를 만듭니다. 개인별 브랜치 하나를 모든 작업에 계속 사용하지 않습니다.
- 브랜치 이름에는 공백을 넣지 않습니다. `dev`와 개인 기능 브랜치는 별도 브랜치이며, 개인 브랜치 이름을 `dev/feature/...`로 만들지 않습니다.
커밋은 변경 내용을 알 수 있는 작은 단위로 작성합니다.
```text
feat: 팀원 프로필 카드 구현
fix: 모바일 메뉴 겹침 수정
style: 공통 헤더 간격 조정
docs: README 실행 안내 추가
```

### Issue 작성

작업을 시작하기 전에 본인이 수행할 내용을 Issue로 등록합니다.
- **작업 목적:** 왜 필요한 작업인가?
- **담당자:** 누가 책임지고 진행하는가?
- **작업 내용:** 구체적으로 무엇을 하는가?
- **완료 조건:** 어떤 결과를 확인하면 끝났다고 판단하는가?
- **작업 범위:** 대상 페이지·파일과 이번 작업에서 제외할 내용
- **참고·협의 사항:** 먼저 정할 내용과 협의할 담당자
한 Issue는 확인 가능한 작업 단위로 작성하고, 범위나 합의가 바뀌면 본문 또는 댓글에 남깁니다. 본문 담당자 표기와 별도로 GitHub Assignees에도 본인을 지정하는 것을 권장합니다.

### PR과 코드 리뷰

PR의 대상 브랜치는 다음처럼 구분합니다. `base`는 변경을 받을 브랜치, `compare`는 변경을 보내는 브랜치입니다.

```text
개인 기능 PR: base: dev  ← compare: feature/minchan-members
배포 PR:      base: main ← compare: dev
```

PR에는 다음 내용을 포함합니다.

- 변경한 기능과 작업 내용
- 수정한 파일
- 관련 Issue 번호
- 직접 확인한 실행·테스트 결과
- UI 변경이 있는 경우 결과 화면

개인 기능 PR은 작성자가 먼저 실행 결과를 확인하고, 다른 팀원이 실제 변경 내용을 검토합니다. 수정 요청이 있으면 반영하고 다시 확인한 뒤 `dev`에 병합합니다.

`dev`에서는 페이지 간 이동, 공통 UI, PC·모바일 화면과 주요 기능을 함께 점검합니다. 공개할 준비가 되면 `dev → main` 배포 PR에 통합 테스트 결과를 남기고 최종 확인 후 병합합니다. `main` 병합은 공개 사이트 배포로 이어지므로 미완성·미확인 변경을 포함하지 않도록 확인합니다.

PR·리뷰 진행 관리 담당자가 있어도 모든 PR을 대신 작성하거나 모든 리뷰를 혼자 맡지 않습니다.

### 병합 충돌 대응

1. 충돌한 파일과 내용을 확인합니다.
2. 관련 담당자와 각 변경의 의도를 공유합니다.
3. 필요한 변경을 함께 반영하도록 내용을 정리합니다.
4. 해결 후 페이지·메뉴·주요 기능을 다시 실행해 확인합니다.
5. 발생 상황, 해결 방법과 확인 결과를 PR 또는 기록 문서에 남깁니다.

### GitHub Pages

| 항목 | 내용 |
| --- | --- |
| 배포 담당 | 정에디 |
| 설정 지원 | 팀장 박민찬 |
| 현재 상태 | 배포 완료·접속 확인 전 |
| 배포 주소 | 실제 배포와 접속 확인 후 추가 |
| 배포 방식 | 브랜치 기반 자동 배포 설정 예정 |
| 배포 원본 | `main` 브랜치의 루트(`/`)로 지정 예정 |
설정 계획은 `Settings → Pages → Deploy from a branch → main → / (root)`입니다.
설정 후 `main`에 변경이 반영되면 GitHub Pages 빌드·배포가 진행됩니다. `dev`나 개인 기능 브랜치의 변경은 공개 사이트에 직접 반영하지 않습니다. 공개 사이트는 빌드·배포가 성공한 뒤 갱신되며, 병합 즉시 반영되는 것은 아닙니다.
배포 후에는 메인뿐 아니라 각 페이지의 링크, 이미지 경로와 주요 동작을 확인합니다. 확인되지 않은 예정 주소를 운영 중인 서비스 링크로 표시하지 않습니다.

## 🪪 출처 및 라이선스
- 외부 이미지·아이콘·글꼴·참고 코드는 원본 출처와 사용 조건을 확인합니다.
- 사용 자료의 이름, 원본 URL, 작성자, 라이선스와 적용 위치를 기록합니다.
- 팀원 사진·소개·연락 경로는 공개 가능한 범위를 확인한 뒤 사용합니다.
- 학번, 개인 연락처, 비밀번호, 토큰, API 키와 `.env` 등 비밀 정보는 게시하지 않습니다.
- 프로젝트 자체 라이선스는 팀 협의 후 결정하며, 결정 전 임의의 라이선스를 표기하지 않습니다.
